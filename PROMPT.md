# ГЕНЕРАЛЬНЫЙ ПРОМПТ
## Фабрика органических лендингов недвижимости Пхукета
### Один репозиторий → ветка на лендинг → свой домен

Версия: 2026-08-28  
Назначение: отдать в разработку как конституцию репозитория.  
Этот документ не про один комплекс и не про один район. Он про систему, из которой собираются все посадочные.

---

## 0. Роль модели / команды

Ты проектируешь и собираешь **монорепозиторий лендингов**.

`main` — каркас, дизайн-система, движок квиза, схема контента, CI, документация.  
Каждая посадочная живёт в **отдельной ветке** и выкатывается на **свой домен**.

Запрещено зашивать в каркас имя комплекса, район, цену, застройщика, телефон, офер.  
Всё уникальное приходит только из конфига ветки.

Каждый лендинг должен:

1. Выглядеть как editorial-luxury продукт, не шаблон агентства.
2. Быть органически здоровым: один интент — один домен.
3. Иметь блок **Фонарь**.
4. Иметь **квалифицирующий квиз** с маршрутом до контакта.
5. Давать **здравые разъяснения** клиенту.
6. Собираться из общих компонентов + локального контента.

Если факта нет в конфиге — писать `[ДАННЫЕ]`. Цифры рынка, yield, юридические схемы, отзывы, «осталось N вилл» не выдумывать.

## 1. Репозиторий

### 1.1. Стратегия веток

```
main                         каркас, пакеты, шаблон, CI, этот промпт
landings/<slug>              полный лендинг под один домен
hotfix/<slug>-<issue>        точечный фикс живого домена
```

Правила:

- Из `main` ветка лендинга создаётся только командой-генератором + заполненным конфигом.
- В ветке лендинга можно менять контент, SEO, доменные ключи, локальные изображения.
- Обратно в `main` из ветки лендинга идёт только общее: баг компонента, токен, улучшение квиз-движка. Контент комплекса в `main` не тащить.
- Одна ветка = один домен = один поисковый интент.
- Не держать 50 доменов на одном URL-пространстве через query `?project=`.

Имя ветки = slug лендинга: `landings/kata-family-condos`, `landings/nai-thon-airport`, `landings/remote-buy`.

### 1.2. Дерево main

```
/
  README.md
  PROMPT.md                         этот документ
  package.json
  /packages
    /ui                             кнопки, типографика, сетка, карточки
    /fonar                          блок Фонаря
    /quiz                           движок квиза + маршруты
    /explain                        аккордеон разъяснений
    /seo                            мета, schema, sitemap, robots
    /analytics                      адаптер событий, без ключей
    /legal                          дисклеймер-шаблон
  /templates
    /landing                        скелет страницы
  /schemas
    landing.schema.json             валидация конфига
    quiz.schema.json
  /tooling
    create-landing.mjs              main → ветка + каркас конфига
    validate-landing.mjs
    build-landing.mjs
  /landings                         в main пусто или только _example
    /_example
      config.json
      content/
      public/
  /.github/workflows
    ci-main.yml
    deploy-landing.yml              деплой по имени ветки
```

В ветке лендинга появляется только:

```
/landings/<slug>
  config.json                       домен, интент, тексты, квиз, CTA
  content/                          md/json блоки, FAQ, разъяснения
  public/                           уникальные фото, og, favicon
  redirects.json                    если нужно
```

Сборка читает `packages/*` + `landings/<slug>` и отдаёт статический сайт в `dist/`.

### 1.3. Стек

Фиксировать в README и не размножать фреймворки без причины.

Рекомендуемый минимум:

- статика: HTML + CSS + vanilla JS  
  или один лёгкий слой (Astro / 11ty), если команда так привыкла;
- стили: Tailwind + токены из `/packages/ui`;
- без jQuery, без тяжёлого SPA, без общей CMS на все домены;
- один лендинг должен открываться как набор статических файлов;
- mobile-first, базовый холст 390–430px, iPad не растягивать.

Если команда выбирает Astro/11ty — квиз и Фонарь всё равно остаются общими пакетами, а не копипастой в 50 веток.

### 1.4. Домены

Каждый лендинг:

- свой hostname;
- свой `canonical` = `https://<domain>/`;
- свой favicon / og-image;
- свои ключи аналитики;
- свой Search Console;
- свой `robots.txt` и `sitemap.xml` только на этот домен.

Между доменами ссылки — обычные внешние.  
Разрешены: «соседний район», «сравнить сценарий», «хаб портфеля».  
Запрещены: одинаковый title на разных доменах, склейка контента, один sitemap на все площадки.

Конфиг:

```json
"domain": "kata-family.example",
"origin": "https://kata-family.example",
"hreflang": [{ "lang": "ru", "url": "https://..." }],
"analytics": { "provider": "none" }
```

Ключи аналитики и пиксели не коммитить в открытый репозиторий. Только имена переменных окружения.

## 2. Органическая концепция

### 2.1. Один домен — один интент

Лендинг закрывает один человеческий вопрос. Не «вся недвижимость Пхукета».

Тип задаётся в конфиге:

| type | Задача |
|---|---|
| `area` | Район: кому сюда, якоря, риски, какие форматы |
| `audience` | Аудитория: семья, инвестор, зимовка, remote |
| `project` | Один комплекс / продукт |
| `scenario` | Механика: off-plan, удалённая сделка, земля |
| `compare` | Два района или два формата |

На одном домене один `type`.  
`project` не дублирует соседний `area` слово в слово. Районный домен говорит о месте, продуктовый — о конкретном инвентаре.

### 2.2. Здоровье на 50 доменах

Обязательно разное:

- H1, title, description
- Фонарь
- лид hero
- 70%+ текста разъяснений
- FAQ
- набор якорей
- пресет квиза и тексты маршрутов
- OG-картинка

Можно общее:

- UI-kit, сетка, тон, шапка/подвал как система
- движок квиза
- юридический каркас формулировок
- события аналитики

Запрещено:

- дверные домены с заменой топонима;
- «лучшая недвижимость Пхукета»;
- гарантия доходности и «без риска»;
- фейковый дефицит, таймер, фейковые отзывы;
- серые схемы владения землёй;
- копирование карточки объекта с портала без своей рамки.

Органический тон: справочник сильного игрока, не давящий оффер.

### 2.3. Перелинковка доменов

В конфиге:

```json
"neighbors": [
  { "label": "Ката vs Карон", "href": "https://...", "rel": "noopener" },
  { "label": "Семейный маршрут", "href": "https://..." }
]
```

На странице 2–5 таких ссылок + одна на общий хаб, если хаб существует.  
Анкор = интент соседа, не «подробнее здесь».

## 3. Конфиг лендинга

Единственный источник правды ветки. Валидируется схемой до сборки.

Минимальный каркас:

```json
{
  "slug": "area-kata-family",
  "domain": "",
  "language": "ru",
  "type": "area",
  "intent": "live",
  "geo": {
    "island": "Phuket",
    "district": "",
    "nearby": [],
    "anchors": []
  },
  "audience": "",
  "propertyTypes": [],
  "ownershipFocus": "",
  "product": {
    "name": "",
    "developer": "",
    "stage": "",
    "completion": "",
    "unitRange": "",
    "entryPrice": "",
    "pricePerSqm": ""
  },
  "brand": {
    "name": "",
    "homeLabel": "",
    "logoAlt": ""
  },
  "seo": {
    "title": "",
    "description": "",
    "h1": ""
  },
  "fonar": {
    "label": "Фонарь",
    "strike": "",
    "body": "",
    "splitYes": "",
    "splitNo": "",
    "ctaLabel": "Разобрать мой сценарий",
    "ctaHref": "#quiz"
  },
  "hero": {
    "eyebrow": "",
    "lead": "",
    "primaryCta": "",
    "secondaryCta": ""
  },
  "quizPreset": "",
  "explanations": [],
  "faq": [],
  "units": [],
  "neighbors": [],
  "cta": {
    "primaryChannel": "telegram",
    "primaryValue": "",
    "afterQuiz": true

    "disclaimer": "default",
    "notOffer": true
  },

```

Пустые коммерческие поля не заполняются генератором. Сборка либо показывает `[ДАННЫЕ]`, либо скрывает блок, если `optional: true`.

## 4. Визуал и тон (общее, без объекта)

Палитра: глубокий чёрный / тёплый графит / песок / тёплый белый / приглушённый teal / тонкое тёплое золото.  
Не киберпанк, не marketplace-синий, не «риелтор 2014».

Типографика: гротеск для UI, антиква/serif для Фонаря и крупных мыслей.  
Много воздуха, сильный контраст. Люди и место — первый план, интерфейс — второй.

Голос: спокойный, точный, взрослый. Короткий абзац. Можно быть острым в Фонаре. Нельзя кричать в разъяснениях.

Писать так, будто человек уже видел десятки объявлений на порталах. Экономить ему месяц хаоса.

Бренд в шапке берётся из `config.brand`. Каркас не знает конкретного имени компании.

## 5. Сборка страницы

Порядок секций фиксирован. Пустые по конфигу секции схлопываются, кроме обязательных.

Обязательные:

1. Header
2. Hero
3. **Фонарь**
4. Кому страница / антикому
5. Квиз
6. Маршрут после квиза
7. Здравые разъяснения
8. FAQ
9. Финальный CTA
10. Footer + дисклеймер

Включаемые по типу:

- якоря района (`area`)
- карточки / мини-шахматка (`project`)
- рамка бюджета, если есть данные
- жизнь после покупки, если в конфиге есть сервисный оффер
- сравнительная таблица (`compare`)

Якоря: `#fonar` `#quiz` `#route` `#explain` `#faq`.

Липкий CTA на мобиле один, вторичный не спорит.

## 6. Фонарь

Не H1 и не слоган hero. Отдельный блок сразу после первого экрана.

Задача: высветить неудобную правду связки «место × аудитория × формат» и отличить домен от портала.

### Формулы (в ветке выбрать одну)

1. Неудобная правда рынка  
2. Кому да / кому нет  
3. Механика вместо прилагательного  
4. Антикаталог  
5. Что остаётся после ключей

### Анатомия

- ярлык `Фонарь` или `Стоит понять до просмотра`
- удар 12–22 слова, serif, крупно
- расшифровка 2–4 предложения
- развилка да/нет
- кнопка на `#quiz`

Визуал: тёмная плашка, тёплый свет по кромке, тонкая золотая линия. Без таймера и скидки.

Запрет: один и тот же удар на двух доменах.  
Проверка при создании ветки: `strike` не совпадает с уже существующими `landings/*/config.json`.

## 7. Квиз

Общий движок в `/packages/quiz`.  
Ветка даёт только пресет: набор шагов, подписи, тексты маршрутов.

### Принцип

Квиз квалифицирует и ведёт. Сначала маршрут, потом контакт.  
4–6 шагов, один вопрос на экран, назад без потери, состояние в `localStorage`, можно закончить анонимно.

Не спрашивать «вам интересна недвижимость?».

### Базовые шаги движка

1. Задача: жить / сдавать / оба / разбираюсь  
2. Формат: апартаменты / вилла в комплексе / отдельностоящая / branded / земля / не знаю  
3. География: этот фокус / сравнить соседа / место не важно  
4. Бюджет: коридоры + «не готов называть»  
5. Горизонт: смотрю / сезон / off-plan  
6. Способ: на острове / удалённо / консьерж  

Пресет ветки может убрать шаг, переименовать ответы, добавить школу / yield-горизонт / готовность к leasehold.

### Маршруты, которые движок обязан уметь

- `fit` — фокус домена совпал  
- `neighbor` — лучше соседний домен  
- `budget` — коридор не бьётся, честно сузить  
- `learn` — человек ещё изучает  
- `remote` — сделка без перелёта  

После последнего шага сразу текст маршрута на странице.  
Контакт только из маршрута: «забрать эту подборку в Telegram».  
Телефон не обязателен, если есть мессенджер.

События: `quiz_start`, `quiz_step`, `quiz_complete`, `quiz_route_<id>`, `cta_click`.  
Провайдер аналитики подключается адаптером, не хардкодом.

## 8. Здравые разъяснения

Пакет `/packages/explain` даёт структуру. Текст — из ветки.

Формат блока: вопрос клиента → 3–6 предложений → «что сделать до резерва» → при необходимости «это к юристу».

Темы подключать по флагу типа, не все сразу:

- кондо и иностранная квота 49%
- вилла / земля: не расписывать обход закона, отправлять к независимому юристу
- Chanote и проверка до депозита
- депозит часто невозвратный
- рассрочка застройщика ≠ ипотека
- сопутствующие расходы
- off-plan: этап, кто управляет после сдачи
- район: шум, уклон, стройка, сезон, кому не подходит
- аренда: вилка и условия, не гарантия
- что сервис после ключей делает и чего не делает

Дисклеймер в подвале один раз: страница не оферта и не персональная юрконсультация.

## 9. Копирайт-правила генератора

H1: `[формат] в [гео] для [аудитории]: [сценарий]`  
Без бренда в H1, бренд можно в title после пайпа.

Title 50–65 знаков, description 140–160, уникальные.

Карточка объекта, если есть:

`тип · спальни · м² · вид · якорь · право · статус · цена или «по запросу»`

FAQ: 4–6 вопросов именно этого домена.

Язык страницы один. `lang` по конфигу. Не мешать абзацы RU/EN.

## 10. Команда создания новой ветки

Разработчик или агент делает только это.

```bash
npm run new:landing -- --slug area-kata-family --type area
```

Скрипт:

1. Проверяет, что `main` чистый.
2. Создаёт `landings/<slug>` от шаблона `_example`.
3. Создаёт ветку `landings/<slug>`.
4. Пишет черновик `config.json` с пустыми коммерческими полями.
5. Говорит, какие поля обязательны для `type`.
6. Не деплоит.

Дальше человек или редактор заполняет конфиг.  
`npm run validate:landing` не пропускает сборку, если нет Фонаря, H1, типа, языка, хотя бы 4 FAQ, хотя бы 3 разъяснения, `domain` пустой на проде.

Деплой ветки:

- preview-домен на PR;
- прод-домен только из `config.domain` + секреты окружения.

---

## 11. Приёмка ветки

Лендинг готов к домену, если:

- [ ] конфиг проходит схему
- [ ] Фонарь заполнен и не совпадает с другими ветками
- [ ] квиз завершается маршрутом без контакта
- [ ] разъяснения без выдуманных норм
- [ ] видно, чем страница не портал
- [ ] 428px без горизонтального скролла
- [ ] один главный CTA, второй спокойный
- [ ] нет пунктов из `forbiddenClaims` и системных запретов
- [ ] title / H1 / FAQ уникальны
- [ ] canonical, og, robots, sitemap смотрят только на свой домен
- [ ] секреты не в git
- [ ] `dist/` открывается без бэкенда

## 12. Как агенту отвечать, когда его просят «сделать лендинг»

Если просят каркас репозитория — собрать структуру `main`, пакеты, схемы, `_example`, README, скрипты. Без выдуманных комплексов.

Если просят новую ветку — сначала потребовать бриф или заполнить только некоммерческие поля и оставить `[ДАННЫЕ]`.

Если просят сразу 50 доменов — отказать в генерации 50 тонких копий. Вернуть матрицу слотов: type × geo × audience, и создать ветки пачками по 3–5 с уникальными Фонарями.

Формат ответа на одну ветку:

1. slug, type, предлагаемый domain-pattern
2. title, description, H1
3. текст Фонаря
4. пресет квиза и маршруты
5. `config.json`
6. контентные файлы
7. список `[ДАННЫЕ]`
8. 3 соседних домена для перелинковки

Без преамбулы «конечно, вот лендинг».
